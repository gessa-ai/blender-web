## Findings

### MAJOR-1 - Pointer Lock acceptance is confused with browser lock state

Commit `b09aa76` treats both `EMSCRIPTEN_RESULT_SUCCESS` and `EMSCRIPTEN_RESULT_DEFERRED` as
successful grabs (`platform_web/ghost/GHOST_WindowWeb.cc:426-451`). The base
`GHOST_Window::setCursorGrab()` therefore stores Wrap/Hide immediately
(`upstream/intern/ghost/intern/GHOST_Window.cc:167-197`), although the deferred request runs only
after a later user-activation event. No `pointerlockchange` or `pointerlockerror` callback is
registered anywhere in the web backend, despite both being available in the pinned Emscripten
API. Escape, deferred denial, browser blur, or another external unlock can consequently leave
GHOST in warp mode after the DOM lock is absent. Mouse translation then keeps accumulating
`movementX/Y` instead of using absolute canvas coordinates
(`platform_web/ghost/GHOST_EventBridgeWeb.cc:229-255`). Active-window disposal also does not exit
or reconcile Pointer Lock (`platform_web/ghost/GHOST_SystemWeb.cc:951-987`).

Both live tests cover successful entry followed only by the application's requested Disable
(`platform_web/ghost/harness/pointer_lock_test.mjs:67-77,128-133` and
`sandbox/wgpu-pipeline-integrated-smoke/live_pointer_lock.mjs:85-112`). They do not cover
rejection, external Escape/loss, blur, or disposal while locked.

The corrective unit must bridge change/error outcomes to the owning WM worker, distinguish
pending from active lock, reconcile GHOST grab state on every loss/error/disposal path, and add
fail-first coverage for those four cases without turning software diagnostics into receipts.

### MAJOR-2 - IME terminal events can be dropped and dead-key resolution is overclaimed

The bounded queue added by `9608169` drops whichever message reaches a full slot or fails
allocation (`platform_web/ghost/GHOST_EventBridgeWeb.cc:118-135`). That includes Commit and End.
There is no terminal reservation, update coalescing, or explicit cancellation recovery, so a
previously delivered Start/Update can leave Blender composition active indefinitely. The
21-mutation source contract checks queue mechanics and counters, but no saturation-to-terminal
recovery behavior (`sandbox/wgpu-pipeline-integrated-smoke/ime_bridge_contract.py:136-171`).

The browser receipts also do not exercise a browser-generated composition or dead key. Both
construct and dispatch untrusted synthetic `CompositionEvent` objects from `page.evaluate()`
(`platform_web/ghost/harness/ime_composition_test.mjs:84-92` and
`sandbox/wgpu-pipeline-integrated-smoke/live_ime.mjs:94-100`). That proves the DOM-to-GHOST UTF-8
ownership path, not OS IME/dead-key integration. Nevertheless commit `7f1b93a` marked
`ime-dead-keys` resolved and described saturation as closed.

This audit changes that ledger row to `partial`. The implementation unit must coalesce disposable
updates or reserve terminal capacity and guarantee End/cancel recovery under saturation and
allocation failure. A separate supported-browser/OS receipt must exercise trusted physical IME
and dead-key input before the row can return to resolved.

### MAJOR-3 - callback retirement is pointer-safe but not registration-epoch-safe

Commit `64a2578` gates queued callbacks by comparing their raw `GHOST_SystemWeb *` userdata to a
single atomic owner (`platform_web/ghost/GHOST_SystemWeb.cc:55-64`). Unregistration clears that
pointer (`GHOST_SystemWeb.cc:667-688`), but replacement registration publishes the same `this`
again (`GHOST_SystemWeb.cc:371-376`). A callback queued under the old registration and delivered
after replacement therefore passes the gate and targets the replacement window.

The browser lifecycle test waits for removal, sends detached input, then recreates the window
(`platform_web/ghost/harness/window_lifecycle_test.mjs:71-109`). It never queues an event before
removal and delivers it after rebinding, while the static contract reports
`queued=owner-gated` (`sandbox/wgpu-pipeline-integrated-smoke/window_lifecycle_contract.py:193-194`).

Use durable per-registration userdata carrying an epoch/token and reject every callback whose
epoch is not current. Add a queue-before-dispose/rebind-before-delivery test, including repeated
replacement, before restoring the ownership claim.

### MINOR-1 - callback registration is not transactional

`GHOST_SystemWeb::registerCanvasCallbacks()` ignores the result of all ten
`emscripten_set_*_callback` calls, then unconditionally sets `callbacks_registered_ = true`
(`platform_web/ghost/GHOST_SystemWeb.cc:650-664`). A selector/API failure can therefore publish a
partially registered window that later claims complete removal. The shipping selector is valid in
the current browser harness, so this is a fail-closed robustness gap rather than a demonstrated
shipping failure. Require all registration results, remove any successful prefix on failure, and
publish the owner/registered flag only after the complete set succeeds.
