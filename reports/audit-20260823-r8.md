# Latest-25 adversarial audit R8 — 2026-08-23

## Outcome

**2 critical / 4 major / 2 minor. All eight findings are open and ordered in
`fix_plan.md`; no receipt or gate was promoted.**

The exact immutable range is `4122d60^..9505bfb`: 25 commits from `4122d60`
through `9505bfb`. It covers the R7 corrections for pending buffer payloads,
layered-clear ordering, upload commit, compute bind-group scope, acquisition and
device-loss lifetime, and scheduler draining (patches 0240–0244), followed by the
R8 callback-lifetime and callback-serialization corrections.
Tracked-source line references below are to commit `9505bfb`; backend line
references are to its canonically applied 221-patch `upstream/` postimage.

The critical defects are browser-product correctness failures, not receipt
inflation. The callback gate serializes callback against callback but not callback
against ordinary owner execution, device-loss cleanup, or the beginning of
destruction. Separately, an accepted VBO upload can clear a newer CPU mutation's
dirty state because the transaction has no generation identity. M3/M4 remain
honestly red.

An independent subagent reviewed the same exact range read-only. It found seven of
the eight findings below and independently confirmed the protected-path,
provenance, author/trailer, hardware, and non-receipt boundaries. The primary
review added the unscoped staging-allocation finding and expanded the callback
finding with the destructor-admission interleaving before recording the shared

## Findings

### CRITICAL-1 — callback serialization does not serialize the owner lifecycle

Pinned WebGPU explicitly permits `AllowSpontaneous` callbacks on an arbitrary or
application thread and warns about locking and state mutation
(`build-dawn/dawn/third_party/webgpu-headers/src/webgpu.h:470-476`). Commit
`5652eff` puts a recursive `delivery_mutex_` around each callback, but ordinary
`GHOST_ContextWGPUWeb` public methods and cleanup never acquire that mutex
(`platform_web/ghost/GHOST_WGPUTransaction.hh:31-74`). Callback-vs-callback is
serialized; callback-vs-owner is not.

The terminal path demonstrates the race directly. `propagateDeviceLoss()` calls
the deliberately non-waiting `cancel()` and then immediately clears readiness,
pending flags, pipelines, surface, queue, and device
(`GHOST_ContextWGPUWeb.cc:489-508`). An already-admitted resize callback can pass
its loss check and then use those same fields through configuration and
publication (`GHOST_ContextWGPUWeb.cc:634-724`). The present and pipeline paths
have the same shape. A normal WM-thread method can likewise read or mutate the
same non-atomic fields while a spontaneous callback holds only the callback-local
lock.

Destruction has a second admission hole. `invalidate()` waits for
`delivery_mutex_` before it sets `accepting_ = false`. Once a destructor has
started behind an active callback, a recursive delivery on the active thread—or
another waiting delivery that wins the mutex race—can still pass the state check
before invalidation closes admission. That accesses an owner whose destructor has
already begun. The existing concurrent-destruction test releases the active
callback without attempting this late delivery, so it remains green.

The smallest regressions hold one admitted callback at a barrier while an owner
method/device-loss cleanup tries to mutate the same state, and start destruction
behind an active callback before attempting nested and queued delivery. They must
prove zero overlap and zero admission after terminal transition begins, while
preserving safe self-destruction. Repair should marshal completions to the owner
thread or provide one reentrant owner-execution boundary shared by callbacks,
public methods, cleanup, and destruction. Admission must close before quiescence
without introducing state/delivery lock inversion.

### CRITICAL-2 — an accepted VBO snapshot can discard a newer CPU mutation

Commit `c9cddfa` adds `upload_transaction_`, but it does not identify which dirty
generation the transaction represents. When upload A is browser-pending,
`WGPUVertexBuffer::upload_data()` leaves `GPU_VERTBUF_DATA_DIRTY` set and returns
(`patches/0242-gpu-webgpu-upload-commit.patch:533-603`). A frontend attribute or
vertex edit can then mutate `data_` to B and set the already-set dirty bit again.
When A accepts, the `transaction_.started()` branch observes only acceptance,
resets the token, and clears the dirty bit (and can free static `data_`) without
ever scheduling B (`patch 0242:606-609`; applied postimage
`upstream/source/blender/gpu/webgpu/wgpu_vertex_buffer.cc:298-349`).

The float buffer-texture expansion has the same stale-generation contract. A
pending expansion transaction is accepted and unconditionally clears
`buffer_texture_buffer_dirty_`, even if a newer source edit raised that same flag
during the pending interval (`patch 0242:622-645`). The queue correctly owns A's
bytes; that does not preserve the fact that B still needs an upload.

The smallest regression schedules sentinel A through the actual VBO frontend,
mutates host data to sentinel B before A's scopes settle, accepts A, and re-enters
upload/bind. It must retain and upload B, for both ordinary and buffer-texture
paths. Repair needs monotonic upload generations, or must consume the dirty bit
when A is scheduled and preserve any newly raised bit through A's acceptance.

### MAJOR-1 — concurrent replay can reorder retained buffer writes

`PendingBufferPayloadQueue::replay()` marks every entry in one deque snapshot
in-flight, unlocks, and calls the replay function separately for each entry
(`patches/0242-gpu-webgpu-upload-commit.patch:322-381`; applied postimage
`upstream/source/blender/gpu/webgpu/wgpu_common.hh:2370-2429`). This permits a
second replay owner to overtake the first.

For retained E1,E2, thread A can mark both in-flight and reserve E1. Thread B can
then retain E3, skip in-flight E1/E2, and reserve E3 before thread A reserves E2.
The ordered scheduler truthfully executes its reservation order E1,E3,E2, which
is not the frontend order E1,E2,E3; overlapping writes leave E2 rather than E3 as
the final value. The mutex and comments claim concurrent frontend retention is
supported, so single-thread assumptions cannot close this contract.

The smallest regression uses barriers around reservation to force exactly that
three-entry interleaving and checks final overlapping bytes as well as scheduler
order in native and wasm32. Repair needs one replay/drain owner, or must reserve
all selected scheduler tickets in deque order before releasing queue ownership.

### MAJOR-2 — fallback device loss can strand asynchronous initialization forever

The fallback device-lost callback only marks `device_state_`
(`platform_web/ghost/GHOST_ContextWGPUWeb.cc:424-434`). If loss arrives after the
request-device callback has started presentable setup but before backbuffer or
configuration validation settles, those callbacks see the lost state and simply
return (`GHOST_ContextWGPUWeb.cc:634-639,680-683`). They neither propagate cleanup
nor call `completeInitialization(false)`.

No later public boundary is guaranteed: `initAsync()` promises to invoke the ready
callback, and the documented startup bridge gates main-loop publication on that
settlement (`GHOST_ContextWGPUWeb.hh:78-83`). This loss ordering can therefore
leave `initialization_settled_` false, a pending flag set, and startup waiting
forever.

The smallest regression loses the device independently while backbuffer creation
and surface configuration are each pending, then delivers the completion and
requires exactly one failed ready settlement. Repair should route device loss
through the serialized owner transition and make pending initialization terminal,
without retaining a raw owner in the device-lost callback.

### MAJOR-3 — the ready callback can destroy its own active `std::function`

`completeInitialization()` invokes the member `on_ready_` directly
(`platform_web/ghost/GHOST_ContextWGPUWeb.cc:468-477`). A legitimate ready
callback that deletes the context destroys that `std::function` and its callable
storage while `std::function::operator()` is still executing. The R8
self-destruction test deletes a synthetic owner from an external lambda; it never
executes this production member-callback path.

The smallest ASan regression completes actual initialization with a ready callback
that destroys its owner and requires no access after deletion. Move the callback
into a local, clear the member, and invoke the local as the final action of the
settlement path.

### MAJOR-4 — large-upload staging allocation is outside implementation scopes

The large buffer-update path creates a mapped staging buffer before calling
`command_encode_submit_scoped()`
(`upstream/source/blender/gpu/webgpu/wgpu_buffer.cc:253-269`). That helper pushes
validation/OOM/internal scopes only after the staging `CreateBuffer()` and mapping
have already happened (`wgpu_common.hh:833-866`). A non-null staging error object
or implementation failure is therefore uncaptured and is not itself represented
by the upload transaction; a later command rejection is not a receipt for the
earlier resource creation.

The integrated test covers literal-null allocation, null mapping, and deferred
encoding/submission rejection, but has no resource error-scope or uncaptured-error
counter (`sandbox/wgpu-buffer-integrated-smoke/integrated_buffer_update_test.cc:430-481,
559-599`). This is precisely the resource seam that the shared transient gate was
introduced to protect elsewhere.

The smallest regression returns a non-null error staging buffer, increments an
uncaptured-error counter when creation is unscoped, and requires rejection plus a
clean exact-byte retry with zero uncaptured errors. Repair should reserve a
transient resource gate for staging creation before the dependent command ticket
and retain both candidate and payload through settlement. A pinned-Dawn control
remains software-only and binds no receipt.

### MINOR-1 — the R8 source gate can certify dead text instead of production structure

`sandbox/audit-r8/run.sh:21-39` counts the string `lifetime->deliver`, rejects only
a narrow raw-`this` capture regex, and searches for one invalidation line. Comments,
dead code, aliases, implicit captures, or an unguarded new callback can satisfy or
evade those checks. The behavior test instantiates a synthetic `OwnerProbe`, not
the production cleanup, readiness, or public-method paths. That is why it reports
serialized owner access while CRITICAL-1 remains reachable.

Replace the census with an explicit structural callsite contract and add
production-shaped callback/owner/loss/destruction regressions. The existing
native/wasm32 and unsafe-ASan controls remain useful once those missing paths are
bound.

### MINOR-2 — the context header contradicts its actual inheritance

`platform_web/ghost/GHOST_ContextWGPUWeb.hh:27-30` says the class does not subclass
`GHOST_Context`; line 54 declares `class GHOST_ContextWGPUWeb : public
GHOST_Context`, and the immediately adjacent M4 note explains the promotion. Drop
or update the stale standalone paragraph so lifecycle documentation describes the
shipping class.
