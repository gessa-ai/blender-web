## Major — T3 classified the wrong adapter and under-validated success

The T3 standalone driver first requested and classified a hardware adapter,
then `GHOST_ContextWGPU::initializeDrawingContext()` made a second independent
adapter request. The verifier never classified `ctx.getAdapter()`. On a host
exposing both hardware and software adapters, the preflight result therefore
did not prove that the context/device under test used hardware.

The shell's hardware mode also treated exit zero as sufficient. It did not
require the exact `GHOST_ContextWGPU adapter` and `T3 VERIFY PASS` lines, reject
duplicates, or reject a contradictory `PROBE_BLOCKED` marker. A hollow or
accidentally weakened zero-return binary could have false-greened the future
T3 proof.

The repair adds the same backend/type classifier to the adapter retained by the
real context, before its device is accepted. Hardware mode now requires exit
zero, exactly one nonempty adapter line, exactly one backend-specific PASS
line, and zero blocked markers. The software control also rejects any hardware
PASS line. A no-allocation parser self-check covers the valid transcript plus
missing-PASS, duplicate-PASS, blocked, duplicate-adapter, and nonzero-status
mutations.

Evidence:

- parser mutations: `ledger/buildlogs/20260821T214823-625333.log`;
- real staged-postimage compile: `ledger/buildlogs/20260821T214826-625459.log`;
- live llvmpipe rejection: `ledger/buildlogs/20260821T214833-625634.log`.

The current software-only host still exits before context creation and binds no
receipt. Actual hardware execution remains owned by `M3-LINUX-REPLAY` after s7.
