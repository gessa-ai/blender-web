## Major findings

### 1. Ordinary text input disappears while the IME textarea owns focus (`55db332`)

`platform_web/ghost/GHOST_SystemWeb.cc:1097-1103` registers raw key-down/up only on the canvas,
while `beginIME` focuses `#bw-ime-input` and the non-composing input handler at lines 720-748 only
clears its value. Pinned Blender starts IME for every non-numeric text button in
`upstream/source/blender/editors/interface/interface_handlers.cc:3621-3640,3917-3920`.
Consequently ordinary ASCII, navigation, Escape, Enter/Backspace, and clipboard shortcuts can
reach neither GHOST nor the composition queue during normal text editing.

The trusted browser repro typed `a`, Backspace, and Enter into the focused textarea. All three DOM
events were trusted and non-composing, but GHOST received zero key or IME events and the textarea
was cleared (`ledger/buildlogs/20260826T030555-241420.log`). Existing keyboard-focus coverage tests
canvas versus an unrelated page control; existing IME coverage synthesizes CompositionEvents and
never types ordinary keys into the textarea.

Required repair: admit raw keyboard/control input from every Blender-owned focus element without
duplicating active composition, and assert trusted ASCII, navigation/control, clipboard, and final
Blender text state.

### 2. Focus-loss generation is not a total-order barrier (`aae9c9a`)

Browser capture publishes only a monotonic generation. Input callbacks may enqueue GHOST events
before `GHOST_SystemWeb::processEvents()` polls that generation at lines 1175-1185; the poll then
appends deactivate/activate behind the newer input. The same-task repro observed exactly
`KeyDown, KeyUp, WindowDeactivate, WindowActivate`
(`ledger/buildlogs/20260826T030555-241420.log`). The focused test proves held-state retirement and
one transition pair, but injects no post-refocus input before waiting, so it cannot prove order.

Required repair: place focus boundaries and input in one ordered queue, or stamp each input with
its event-time focus generation and reconcile every preceding loss before input mutation. Assert
blur -> refocus -> immediate key/mouse Down ordering without an intervening wait.

### 3. A simultaneous second window splits manager and canvas ownership (`d343e9e`)

`GHOST_SystemWeb.cc:1655-1667` binds `window_`, callbacks, hit testing, presentation, and first-pixel
state only for the first valid window, but lines 1668-1671 add and activate every later valid
window. The manager can therefore report B active while the single-canvas event/presentation path
still targets A. The lifecycle test disposes A before replacement and never creates two live
windows. `notes/m4-windowed-boot-recon.md` already defers multi-window, but the ledger had no named
row.

Required repair: fail closed on a simultaneous second `createWindow()` and test that behavior,
until coherent per-window canvas/input/presentation routing exists. This audit adds the explicit
`ghost-web-multi-window` deferral; it does not claim the current source defect fixed.
