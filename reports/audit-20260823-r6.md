# Latest-25 adversarial audit R6 — 2026-08-23

## Outcome

**0 critical / 5 major / 0 minor. All five majors are open and ordered in `fix_plan.md`.**

The exact range is `ba828d6^..e4ad1d4`: 25 commits from `ba828d6` through `e4ad1d4`.
It covers patches 0220–0229's framebuffer, texture, bind-group, vertex/index, shader-layout,
and layered-clear transactions plus the browser present and window-publication transactions.

The most pervasive finding is that the new device-free failure seams model WebGPU failure as a
null handle, while pinned Dawn returns a non-null error object for the validation failures those
transactions claim to reject. This is parity-inadequate proof, but no strict receipt, product
profile, result flag, or milestone promise was promoted: M3/M4 remain honestly red. It is
therefore classified major rather than a critical receipt falsification.

An independent subagent reviewed the same exact range without editing files. It independently
found the Dawn error-object mismatch, ordinary framebuffer clear commit ordering, browser resize
extent mismatch, and surface-less window publication. The primary review additionally found the
bind-group completeness defect below.

## Findings

### MAJOR-1 — null-only WebGPU “validity” accepts Dawn error objects

Affected commits include `5b98d6c`, `e4f860d`, `f134090`, `ef53318`, `259a2e5`, `121d696`,
`9d8c391`, `fb38385`, `8bb9908`, `844e683`, and `1ba3e94`. Their shared helpers treat only
`handle == nullptr` as failure and the native/wasm32 tests use integer-like fake handles whose
sole failure state is zero.

Pinned Dawn instead makes and returns non-null error objects after validation/resource failure:

- bind groups and bind-group layouts: `build-dawn/dawn/src/dawn/native/Device.cpp:1204-1221`;
- buffers and command encoders: `Device.cpp:1224-1301`;
- pipeline layouts, render pipelines, shader modules, and textures:
  `Device.cpp:1364-1371,1450-1488,1522-1529`;
- invalid render passes and finished command buffers:
  `build-dawn/dawn/src/dawn/native/CommandEncoder.cpp:1419-1422,1681-1687,2325-2334`;
- queue submission returns `void` and consumes the validation error internally:
  `build-dawn/dawn/src/dawn/native/Queue.cpp:169-178`.

Audit commit `c7050ce` adds a runtime control against that exact pinned Dawn. It deliberately uses
the available llvmpipe software Vulkan adapter and prints `SOFTWARE_CONTROL_NON_RECEIPT`; it can
bind no receipt, profile, or milestone result. All eight invalid buffer, bind-group layout,
pipeline layout, bind group, shader, texture, texture-view, and render-pass/command cases return
non-null objects while an error scope reports validation:

`DAWN_ERROR_HANDLE_AUDIT_PASS cases=8 null_guards_miss_validation=8
SOFTWARE_CONTROL_NON_RECEIPT`

The target build and control run are `20260823T075955-2549288` and
`20260823T075956-2549286`. In contrast, the existing integer-handle integrated tests remain green
in `20260823T080347-2552631` and `20260823T080401-2553449`; that contrast is the reproduced proof
gap, not product success.

Consequences include publishing/caching error bind groups, layouts, pipelines, textures, passes,
and command buffers; reporting layered clears committed after an error submission; and advancing
browser first-pixel/present counters even when no valid frame reached the queue. Repair must derive
success from exact CPU-side preflight or completed error-scope status, not handle truthiness.

### MAJOR-2 — ordinary framebuffer load actions commit before the draw command

`WGPUFrameBuffer::begin_load_pass()` changes color and depth actions from `CLEAR` to `LOAD` while
assembling the pass descriptor (`upstream/source/blender/gpu/webgpu/wgpu_framebuffer.cc:1518-1522,
1562-1581`). A later color/depth attachment view can still fail before `BeginRenderPass`; after
pass creation, vertex/index resolution, bind-group assembly, `Finish()`, or submission can fail in
the direct, indirect, multi-viewport, or immediate caller.

The retry then loads stale pooled attachment contents because the one-shot clear was already
consumed. Patch 0229 protects only the separately materialized all-layer clear; it does not stage
the ordinary render-pass load operations. The smallest regression starts with two clear
attachments, injects failure while creating the later view or bind group, and requires both load
actions to remain `CLEAR` for retry.

Repair should carry a pending color/depth commit token out of pass assembly and apply it only after
all locally checkable resources, the finished command buffer, and the queue submission boundary
succeed. Truthful validation success is also dependent on MAJOR-1.

### MAJOR-3 — an empty/partial binding list is confused with an empty shader layout

Patch 0224 makes compute return a valid “no group” state whenever assembled `entries` is empty
(`upstream/source/blender/gpu/webgpu/wgpu_backend.cc:161-164`). Ordinary batch and immediate paths
likewise skip group creation solely on `entries.empty()` (`wgpu_batch.cc:581-593`,
`wgpu_immediate.cc:238-250`).

That is not a layout census. `WGPUContext::append_resource_bind_entries()` silently omits absent,
invalid, stale, or wrong-kind resources, while `WGPUShader::surviving_bindings_` records the exact
bindings retained by final WGSL (`wgpu_shader.cc:2622-2639`). A shader with required surviving
bindings can therefore reach dispatch/draw with no group, or create a non-null error group from a
partial entry list. WebGPU bindings are not optional. This also contradicts Class 38's stated
requirement to distinguish a genuinely empty resource layout from a required group that failed.

Repair should compare the unique assembled binding IDs with the exact surviving layout set,
including internal push-constant and multi-viewport bindings, before encoder/pass creation. Tests
must cover genuinely empty, complete, required-but-empty, and partial sets.

### MAJOR-4 — browser resize can pair a new surface with the old backbuffer

Commit `844e683` publishes `width_`/`height_`, configures the surface, and sets `configured_`
before attempting backbuffer replacement (`platform_web/ghost/GHOST_ContextWGPUWeb.cc:348-400`).
On a literal null replacement, `texture_replace_if_valid()` preserves only the old texture and
`backbuffer_w_/h_`; the authoritative and surface extents are already new.

`presentBackbuffer()` does not require those extents to match and does not retry the pending
allocation. Its fullscreen `textureLoad` can consequently read beyond the old texture, yielding
black/mismatched output. The device-free test models texture publication only, not the surface,
authoritative, and texture extents whose coherence Class 43 claims.

Repair should allocate and validate the candidate before configuring/publishing the complete
size-bound state, or retain an explicit pending resize while the previous surface configuration
remains usable. Present must require coherent extents and retry without depending on a second
browser resize event. MAJOR-1 remains a prerequisite for recognizing an error texture.

### MAJOR-5 — a WebGPU window without a present surface is still published

Commit `472d9b1` correctly derives `GHOST_WindowWeb::valid_` from
`setDrawingContextType()`, then rejects an invalid candidate before active-window, callback,
manager, or event publication. The child status is nevertheless too weak:
`GHOST_ContextWGPUWeb::initializeDrawingContext()` skips `finishSetup()` when the canvas is
unresolvable, ignores `finishSetup()`'s internal early return when `CreateSurface` fails, then
unconditionally sets `ready_` and returns `GHOST_kSuccess`
(`platform_web/ghost/GHOST_ContextWGPUWeb.cc:164-182,308-345`).

Thus `GHOST_SystemWeb::createWindow()` publishes and emits the initial size event for a window
that cannot present (`platform_web/ghost/GHOST_SystemWeb.cc:551-596`). There is no later setup
call in the deferred branch. The five-case fake window test proves only propagation of a supplied
setter status, not the shipping context's surface failure status.

Repair should make windowed surface creation, configuration, and initial backbuffer readiness
return a status to the context/window constructor. Any deliberate device-only mode must be an
explicit separate mode, not a presentable window reported as ready.
