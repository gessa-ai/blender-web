# P0-I/J deterministic freeze escalation — 2026-08-29

## Outcome

The same driver-operated Apple freeze survived six consecutive linked candidates, so this item
crossed GOAL.md's five-attempt paging threshold. The failed `.wasm.orig` generations were
`5fea52ef8bc9`, `b326a3be5331`, `025682159147`, `f6a096b53f13`, `e5629d6d0867`, and
`e61df1b64f7b`. Each reproduced the deliberate slow/sparse sequence: view cycle, Select All,
Deselect All, one orbit, then pixel-identical later input. Those are authoritative hardware
failures; no software-adapter result below supersedes them.

The current investigation split the filed interaction into native boundaries instead of applying
another redraw/drain guess. A projected Cube click starts the asynchronous WebGPU selection
session, but its first cold attempt blocks in `DRWContext::engines_init_and_sync()` before the
selection modal is installed. On the fallback diagnostic lane, 36 `*_selectable` overlay shader
variants compile inline while `GCaps.use_main_context_workaround` is active. The bounded stage
trace held at engine-init stage 80 throughout that interval, then the selection loop completed and
the continuation became modal.

The remaining freeze mechanism was WM return-code semantics. Blender's event system maps
`OPERATOR_RUNNING_MODAL | OPERATOR_PASS_THROUGH` to `WM_HANDLER_BREAK | WM_HANDLER_MODAL`, so the
selection continuation's supposed navigation pass-through still prevented the viewport navigation
keymap from seeing middle-mouse events. Returning bare `OPERATOR_PASS_THROUGH` for navigation keeps
the modal handler installed but returns `WM_HANDLER_CONTINUE`; state-changing ordinary input
continues to use the bounded retained-input FIFO.

## Candidate evidence

Numbered patch 0315 implements the navigation routing. Patch 0316 exposes monotonic selection-loop
start/completion counters plus bounded draw/shader stages, so a hardware failure can distinguish
another cold synchronous compile from a modal-routing failure without changing selection, redraw,
or presentation policy. The exact slow/sparse producer sends one isolated navigation orbit while
the selection remains unfinished and requires it to invoke/confirm/retire immediately with changed
native view state and pixels; the continuation must then select exactly Cube and retire cleanly.

Five consecutive local runs passed that contract. The final relinked run proves the selection
modal remained active during the navigation orbit and records two retired
`VIEW3D_OT_rotate` invocations, selection shader kind/stage `3/15`, selection loop start/complete
`5/5`, Cube selected, no queued modal input, and zero GPU continuation, selection-readback, page,
or lifecycle errors:

- `ledger/buildlogs/20260829T154855-103641.log`
- `ledger/buildlogs/20260829T155034-105089.log`
- `ledger/buildlogs/20260829T155118-105576.log`
- `ledger/buildlogs/20260829T155437-107911.log`
- `ledger/buildlogs/20260829T160246-113269.log`

These runs use rejected SwiftShader and bind diagnosis/software stability only. P0-I/J remain open.
The closure bar is unchanged: the driver must pass 10/10 independent slow/sparse Apple runs against
this exact linked generation, followed by the same-generation P0-E and zero-artifact interaction
gauntlet.
