### MINOR-2 — the committed dashboard is stale and derives "M3 DONE" from a substring grep
`reports/dashboard.md` (regenerated at `071fcd3`) is "the human's only interface" and GOAL
demands it be truthful. Two defects, both verified against committed state:

1. **Stale/contradictory suite cell.** `reports/dashboard.md:36` shows
   `gpu static_shaders compile | 951/973`, sourced from `notes/gpu-gate-census.md`
   (git-dated 2026-08-05T23:24). The authoritative, committed gate result
   (`ledger/results/m3.json`, 2026-08-06T11:43:26Z) and my live re-run both say **956/973**
   (r17 patch 0097 moved 951→956; the notes file was never refreshed). The dashboard's own
   milestone row marks **M3 DONE** citing the gate whose floor is `>=956` — so the interface
   shows a milestone as complete next to a suite number that would *fail that milestone's own
   gate*. It under-reports (951 < 956), so it is conservative, not inflating — but it is
   internally self-contradictory. Root cause: `scripts/dashboard.sh` sources the gpu rows from
   the hand-maintained `notes/gpu-gate-census.md` (`dashboard.sh:85,210-224`) instead of the
   authoritative `ledger/results/m3.json`, which existed *before* the dashboard was generated.

2. **Fragile DONE detection.** `scripts/dashboard.sh:131` derives milestone completion via
   `git log --all -1 --grep "M3_GPU_BACKEND"` — a raw-substring match on any commit message on
   any branch, **not** the `<promise>M3_GPU_BACKEND</promise>` tag GOAL specifies. No commit in
   history emits that promise tag (checked `%B` across `--all`); the match is `52ec8a5`'s casual
   phrase "M3_GPU_BACKEND receipts". M0/M1/M2 show DONE legitimately via their passing result
   JSONs (`res_pass`), but M3's `MILESTONES` slot passes `None` for results (`dashboard.sh:122`)
   so its DONE rests solely on the substring grep. Any future commit merely *mentioning* a
   milestone token would flip that milestone to DONE.

Severity note: M3's gate **is** genuinely green (I independently re-verified 148/8/2, 956/973,
12/12), so the DONE is *substantively correct* and nothing is falsely claimed complete — hence
MINOR, not MAJOR. But for the human's sole interface the derivation is unsound and the suite
cell contradicts the gate. (The r20 checkpoint — excluded churn — already notes "dashboard
static cell 951 is one regen behind 956", confirming driver awareness; the committed dashboard
is still stale.)

### MINOR-3 — `blit_color_render` header comment contradicts its body and its actual behavior
`patches/0098-gpu-webgpu-cross-format-region-blit.patch`; applied at
`upstream/source/blender/gpu/webgpu/wgpu_context.hh:182-183` and `…/wgpu_context.cc:314-317`.
The header comment claims the blit *"Reproduces the copy's texel mapping exactly (src texel
(i,j) -> dst texel (dst_x + i, dst_y + j), no flip), so it is a drop-in replacement for the
rejected copy."* The body comment (and the shader) say the opposite: the fullscreen-triangle
emits `o.uv = vec2f(x, y)`, so the destination top samples source v=1 (bottom) — a deliberate
**vertical flip** relative to `CopyTextureToTexture`, described in-code as *"the blit samples
with uv.y = y (NOT the straight-copy 1 - y) … the straight copy renders … upside-down, this
sign lands them upright"* and *"verified in-tab"*. The behavior is correct for the
window-composite use (bottom-up ADR-005 offscreens → upright browser-composited surface); only
the header is wrong. Risk: a maintainer trusting *"no flip / drop-in replacement"* could reuse
`blit_color_render` in a same-orientation context and get an unexpected flip. Fix: correct the
header to state it flips vertically (offscreen bottom-up → upright surface). Behavioral, no test
impact — the window path is not covered by any oracle test.

## Checked and CLEAN (coverage map)

**Parity theater (brief item 1) — every flagged item is principled, not test-shaped:**

- **Bind-group chain 0092 / 0099 / 0101.**
  - `0092` (draw/immediate/compute bind-group assembly) is a **real** implementation — shared
    `append_resource_bind_entries` + `remap_*_binding` + sampler cache; 26 function-body
    markers, **zero** TODO/FIXME/no-op/abort added. The round *fills* prior empty stubs
    (`0085`: "GPU_vertbuf_bind_as_ssbo … were empty stubs, so …" now implemented). Census held
    148/158 with `0092` in (identity remap for single-resource shaders).
  - `0099` null-buffer guard is **honest recoverable degradation, not a bug-hider**. It drops
    resourceless entries only to prevent an *uncaught JS TypeError* (`createBindGroup` null
    `buffer`) that hard-halts the WM render loop; Dawn still emits a validation warning on the
    resulting incomplete group. It does **not** touch the gate census (those tests build
    complete groups — independently confirmed 148/8/2 holds). Caveat (as with audit-20260805
    MINOR-2): the drop is silent on Blender's side, so a genuine frontend resource-assembly bug
    in interactive use would degrade without a Blender-side diagnostic — but the root-cause fix
    (explicit layouts) is the driver's stated next step and landed r20 (`0103`, excluded).
  - `0101` is **more** correct, not a dodge: `is_uniform_binding`/`is_storage_binding` replace
    the generic `is_buffer_binding` so a UBO can never land on a Storage slot and vice-versa
    (matches the layout kind); the keep-first `@binding` dedup is defensive and documented.
    (Trivial: `(void)is_buffer_binding` leaves the now-unused lambda in place — cosmetic.)
- **Y-flip pair 0096 + 0098.** `0096` converts the ADR-005 clip-space Y negation into a
  pipeline-overridable spec constant (`constant_id 1000`, default `0xBF800000` = −1.0f). The
  **offscreen path is byte-identical** — the override is simply *unset* so every offscreen
  pipeline keeps −1.0f, and the added `layout(constant_id=1000)` declaration introduced **no
  compile regression** (static_shaders held 951→956 across the round; I re-ran → 956). The
  window backbuffer alone gets +1.0f (winding swap correspondingly dropped), a real coordinate
  reconciliation for a browser-composited surface that no oracle test exercises. `0098`'s blit
  is likewise a genuine bottom-up→upright reconciliation (only its header comment is wrong —
  MINOR-3).
- **UBO 16 KiB pad 0100** is honest over-allocation, not a masked derivation bug. Blender caps
  UBOs at the 16 KiB GL guarantee; padding every UBO to that ceiling makes the bound size
  satisfy WGSL auto-layout's `minBindingSize` (derived from the full `ViewMatrices view_buf[64]`
  struct = 16384). Correctness holds: `update()`/`clear` write only the real payload; the tail
  is zero-init and unindexed for single-view. The clean fix (explicit layouts / per-binding
  `minBindingSize`) is acknowledged in-code and landed r20 (`0103`). *Observation, not a
  finding:* the in-code cost estimate ("a handful of UBOs, <2 MiB") is unverified and likely
  optimistic — the pad hits **every** UBO regardless of size (a 64 B UBO → 16 KiB), so a
  viewport with many small UBOs could exceed the stated bound; still single-digit MiB, no
  correctness effect.
- **`scope_m3` does not launder failures.** The installed scope (byte-identical to the
  `sandbox/m3-scope-draft` fragment) maps all 10 non-PASS census tests to a registered
  `deferred.json` id or a documented blacklist group, and its honesty guards are real and fire
  as designed: **un-defer** (a deferred test that now PASSES → census RED, `run.sh:127,146`),
  **new-failure** (any unmapped non-PASS → RED, `:130,145`), **vanished-expectation** (a mapped
  test that disappears → RED, `:135-147`), plus `deferral_consistency` cross-checking that the 5
  gate deferral ids exist in `deferred.json` and the 4 blacklist tokens are documented. I
  re-ran the census one-per-process: 148/8/2, matching.
