## Findings

### CRITICAL-1 — pending persistent creation drops one-shot SSBO/UBO payloads

Commit `b3a0abb` makes persistent buffer publication wait for completed browser error
scopes. `ScopedHandleCache::get_or_create_scoped()` intentionally returns an empty handle
while that scope is pending (`upstream/source/blender/gpu/webgpu/wgpu_common.hh:660-699`),
and `Buffer::create_scoped()` therefore reports false on the first call
(`wgpu_buffer.cc:150-196`). That is correct for handle publication but its callers still
implement the old synchronous contract.

`WGPUStorageBuffer::update()` and `WGPUUniformBuffer::update()` return immediately when
`ensure()` reports the pending creation and retain no copy of the caller's bytes
(`wgpu_storage_buffer.cc:155-175`, `wgpu_uniform_buffer.cc:92-108`). Their frontend create
entry points invoke `update()` exactly once for the initial payload
(`upstream/source/blender/gpu/intern/gpu_storage_buffer.cc:69-86`,
`gpu_uniform_buffer.cc:198-211`). Browser scope settlement publishes an empty allocation;
nothing replays the initialization. Updates and clears arriving during the same pending
window are lost for the same reason.

The integrated creation test explicitly calls creation again after settlement and checks
only an indexed payload
(`sandbox/wgpu-buffer-integrated-smoke/integrated_buffer_create_test.cc:442-504`), so its
green result does not exercise the real one-shot API contract. The
smallest regression delays scope completion, calls the actual SSBO/UBO create API once
with sentinel bytes, settles creation, and requires those bytes to be queued without a
second frontend call. Repair must retain or transactionally initialize every payload that
arrives while creation is pending.

### CRITICAL-2 — all-layer load clears submit after the draw they initialize

Commit `4a1821b` stages all-layer clear completion but reserves the operations in the
wrong order. `command_encode_submit_scoped()` reserves the outer draw ticket before it
runs the encode callback (`upstream/source/blender/gpu/webgpu/wgpu_common.hh:732-758`).
Direct batch encoding then calls `WGPUFrameBuffer::begin_load_pass()`
(`wgpu_batch.cc:609-616`), which calls `materialize_layered_loadstore_clears()`
(`wgpu_framebuffer.cc:1586-1635`). Each materialized layer clear creates a nested command
transaction and therefore a later scheduler ticket (`wgpu_framebuffer.cc:952-1064,
1076-1123`).

The scheduler is FIFO by reservation, so the resulting queue order is draw then clear.
Meanwhile the clear transaction has already staged the attachment, causing the draw pass
to choose `Load` instead of `Clear` (`wgpu_framebuffer.cc:1688-1693`). The draw can read
stale pooled attachment contents, and the late clear then overwrites its output. The
existing integrated cases prove tracker stage/complete bookkeeping only; they never trace
the nested command order.

The smallest regression records scheduler submission order when an outer draw materializes
an array-layer load clear and requires clear then draw. Repair must reserve/complete the
materialized clears ahead of dependent drawing, without blocking the browser event loop,
and commit the shared load-action generation only after both stages validate.

### CRITICAL-3 — browser uploads publish success before validation and discard retry state

`Buffer::update_sub()` starts a scoped direct queue write, ignores its completion, and
returns true immediately (`upstream/source/blender/gpu/webgpu/wgpu_buffer.cc:218-230`).
The staged command path likewise returns true under `__EMSCRIPTEN__` before its atomic
acceptance state can settle (`wgpu_buffer.cc:249-267`). This asynchronous contract began
in pre-range `d5029d5`; `b3a0abb` rewrites the allocation lookup in the same function but
does not close the existing commit gap.

On that immediate true, static VBO upload frees its CPU data and clears the dirty flag
(`wgpu_vertex_buffer.cc:316-337`). Deferred UBO upload ignores the return value and frees
its owned `data_` unconditionally (`wgpu_uniform_buffer.cc:72-89`). If the browser scopes
reject a non-null error object, the scheduler cancels dependent same-epoch work, but a
clean later epoch has neither dirty state nor host bytes to retry. This contradicts the
retry semantics claimed by the new ordered transactions.

The smallest regression delays and rejects the upload scopes, then asserts that neither
`update_sub()` nor its VBO/UBO callers publish committed success and that the exact owned
bytes remain available for a clean next-epoch retry. Repair needs an explicit asynchronous
upload transaction; caller state may commit only from its accepted completion.

### MAJOR-1 — compute bind-group creation remains outside implementation error scopes

Commit `fd04ebb` verifies binding-ID completeness but `build_compute_bind_group()` still
calls `create_bind_group_checked()` before any command error scope and accepts any non-null
handle (`upstream/source/blender/gpu/webgpu/wgpu_backend.cc:133-178`). The helper is a raw
`device_.CreateBindGroup()` (`wgpu_context.cc:862-897`). Direct and indirect compute start
their scoped command transactions only afterward (`wgpu_backend.cc:215-229,266-280`).

Pinned Dawn's validation failures return non-null error bind-group objects, as the existing
software control already demonstrates. Compute can therefore publish that object while its
creation error is uncaptured; the later command may fail, but creation was neither accepted
nor retry-gated as the transaction claims. The current source gate counts guards/call sites,
not scope placement.

The smallest regression supplies a non-null error bind group plus an uncaptured-error
counter and requires creation inside completed implementation scopes before dispatch work
can be published.

### MAJOR-2 — fallback adapter/device callbacks can dereference a destroyed context

The destructor only clears `callback_lifetime_`
(`platform_web/ghost/GHOST_ContextWGPUWeb.cc:175-180`). The spontaneous adapter and device
request completions capture raw `this` and do not capture or check that lifetime token
(`GHOST_ContextWGPUWeb.cc:391-402,446-467`). Destroying a fallback context while either
browser request is pending therefore leaves a use-after-free callback.

The raw captures predate this audit range, but `0b8c500` and `2e2f560` add further owner
calls to those callback bodies while their device-loss note claims callback-safe lifetime.
The integrated lifetime case is an unrelated synthetic shared-state lambda
(`sandbox/wgpu-pipeline-integrated-smoke/integrated_pipeline_test.cc:2551-2576`); the
source gate slices only the device-lost callback.

The smallest regression delays each request completion, destroys the context, and delivers
the callback under ASan. Repair must keep acquisition state independent of the owner, or
capture a weak/shared token and perform no owner access after invalidation.

### MAJOR-3 — fallback device loss does not immediately cancel outstanding work

Commit `2e2f560`'s device-lost callback only marks the shared `device_state_`
(`platform_web/ghost/GHOST_ContextWGPUWeb.cc:409-416`). Terminal propagation clears
`callback_lifetime_` only when a later public boundary calls `deviceIsUsable()` and then
`propagateDeviceLoss()` (`GHOST_ContextWGPUWeb.cc:480-527`). Already-pending resize,
pipeline, and present completions check only the still-true lifetime token
(`GHOST_ContextWGPUWeb.cc:646-712,766-802,891-962`).

Consequently a completion can publish configuration/pipeline state, call `queue.Submit()`,
or advance `note_present()` after loss and before another public entry point observes it.
That contradicts `notes/m4-ghost-device-loss-propagation-20260823.md`, which says the first
loss disables outstanding callbacks and clears pending transactions.

The smallest regression starts each asynchronous transaction, signals loss before scope
completion, and requires no Configure/publication/Submit/present note. Each completion and
submission closure must consult the shared terminal device state directly; owner cleanup
may remain a later public-boundary action.

### MAJOR-4 — poisoned queue drain is recursive and failed epochs grow without bound

This scheduler defect originated in pre-range `d5029d5`, but the range's buffer and command
transactions depend on it. A canceled front entry invokes `finish(false)`, which immediately
calls `start_ready()` again (`upstream/source/blender/gpu/webgpu/wgpu_common.hh:276-319`). A
single browser validation failure followed by a long ready queue in the same epoch therefore
drains one recursive stack frame per cancellation. Existing tests cover only a handful of
followers, not a product-sized burst.

Every failed frame also inserts its epoch into `failed_epochs`; the set is cleared only on
64-bit epoch wrap (`wgpu_common.hh:268-272,311-319,372-379`). Persistent validation failures
therefore retain one epoch forever per failed frame.

The smallest regression fails a blocked head in front of 100,000 resolved followers and
requires bounded-stack iterative cancellation, then advances many failed epochs and requires
pruning once no queued entry can reference them.
